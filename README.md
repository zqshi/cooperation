# Tandem（协动）

> 让团队围绕任务与 AI Agent 协同交付，让每次执行的经验成为项目下一次工作的上下文。

**Tandem** 是面向研发团队的人机协同平台。Agent 作为默认执行者，人退到规格、例外与验收三个位置；平台把 Agent 的概率性产出，转化为组织可信任、可验收、可审计、可计量的确定性交付，并在 Agent 世代更替中保持这一能力不贬值，同时让项目上下文持续沉淀、使同类任务越做越省。

> **当前状态：** 本仓库为产品方案 + DDD 技术设计文档 + 高保真可交互静态原型，**尚未接入**真实任务系统、Agent 执行与持久化后端。原型使用模拟数据，按真实集成语义实现交互逻辑（状态映射、验收门铁律、审计事件 Schema）。

---

## 它解决什么问题

团队开始用 Agent 后，挑战不在"能不能生成代码"，而在**敢不敢把活交给 Agent**：

- **产出是概率性的** —— 会失败、跑偏、超预算、卡住；能力真实，但可靠性是统计的，不是确定的
- **责任无法转移到机器** —— "谁做的、何时、花了多少、依据什么、谁确认的"必须能回答
- **Agent 会换** —— 押注单一 Agent 的平台必然随代际失效
- **资料越堆越多却无复利** —— 知识库中心主义，无人对交付负责
- **交付责任无法闭合** —— 任务意图、验收标准、执行现场分散在三处

问题不在单个环节不够快，而在**组织对 Agent 产出的信任门槛降不下来**。Tandem 的每个功能都要能回答："它如何降低组织的信任门槛？" —— 平台本质是一台**信任机器（Trust Machine）**。

## 一句话理解

**任务是唯一一等公民，上下文是一等服务。**

- **任务回路**回答"这次交付是否成立"
- **上下文回路**回答"下次交付是否更容易成立"

确定性交付立竿见影，复利资产越用越值钱。

## 核心价值

### 1. 任务是唯一一等公民

任务是团队与 Agent 之间的**执行契约**，承载意图、验收标准、计量与责任，跨越 Agent 世代存续。会话只是契约的执行态投影，可替换、可失败；Agent 是可替换的履约方，平台对其保持中立。删除任务，平台归零。

### 2. 上下文是一等服务

上下文承载复利能力，独立建设 API、存储、治理与度量。但它是**任务拉取型**服务，不是任务驱动源 —— 任务按需检索上下文，上下文不主动"推"工作。否则平台会滑向知识管理产品。

### 3. 人负责交付判断

铁律：**Agent 最多推进到 `in_review`，`done` 只能由授权人员确认。** Agent 提交结果与证据，人决定通过、打回或阻塞。责任不可转移给机器。

### 4. 双回路复利

完成任务后，Agent 输出与决策记录先关联来源任务、经治理（权限 / 来源 / 版本 / 质量）后，才进入后续任务可检索的上下文。验收结果与返工原因反哺上下文质量标签 —— 未经治理的产物不自动成为可信上下文。

### 5. 项目是协作与复利的边界

项目承载成员、任务板与共享资产，是多租户账本的隔离边界。同类任务越做越省，跨版本累积。

## 协同闭环

```text
项目中的业务信号
       ↓
任务板创建 backlog 卡片（信息不完整时先澄清）
       ↓
团队受理、讨论并澄清缺失信息
       ↓
确认任务契约（目标 / 范围 / 验收标准 / DoR）
       ↓
派发 Agent 执行，持续观察进展与证据
       ↓
Agent 只能推到 in_review，提交结果与证据
       ↓
人工验收：通过 → done / 打回返工 / 阻塞升级
       ↓
产物沉淀到项目，经治理后供后续任务引用
```

任务状态沿用七态：`backlog` · `todo` · `in_progress` · `in_review` · `blocked` · `done` · `canceled`。三处责任转移点（**创建→派发、执行→in_review、验收→done/打回**）分别对应上下文回路的**拉取、沉淀、校准**。

## 适合谁

**面向内网研发团队 —— 有 Agent 协同交付诉求、且需要把交付责任闭合的组织。**

- **研发负责人**：分派、看进度、控成本 —— 任务级账本、证据与成本一屏可查
- **执行工程师**：写清需求、处理例外、验收 —— DoR 模板、证据包、可回退返工
- **平台 / 安全管理员**：租户、权限、审计 —— 实例隔离、统一审计、预算熔断

**不适合：** 不接受 Agent 参与执行、坚持纯人工编码的团队；只想要单个 Agent IDE 提效、不需要组织级验收与归因的个人；要求 Agent 自动完成 / 自动合并而无需人把关的场景（这违反责任公理）。

## 技术选型候选

> 以下为**设计候选选型，非已落地技术栈**。开源覆盖度仅适用于任务 / 执行 / 治理 / 自动化主链路，不能表述为完整平台覆盖度。版本、许可证、上游活跃度、多租户能力与资源基线必须在 Phase 0 实测核验。

| 层 | 候选 | 角色 |
|---|---|---|
| 任务源 | dashi-taskboard（Apache-2.0） | 任务板 + `in_review` 人验收门 |
| 执行面 | OpenHands Agent Canvas（MIT） | ACP 多 Agent（Claude Code / Codex / OpenHands / OpenCode）+ Automations |
| 上下文服务 | **自研（一等服务）** | 任务拉取型项目记忆 —— 分层、治理、检索、注入、命中度量 |
| 产物服务 | **自研（支撑服务）** | 可引用资料的登记、摘要、索引与引用；代码仍在 Git |
| 接入薄层 | 自研 | 信号接入 / 受理（生成积压卡→待办）+ 调度回写 + SSO + 审计聚合 + 通知 |
| 治理 | oauth2-proxy + LiteLLM + Langfuse | SSO + 按团队多实例租户隔离 + 预算 + 成本 / trace |
| 编排 | Automations → Temporal | Phase 1 用 Automations；Phase 2 引入 Temporal 跨天流程 |

**薄层为什么薄：** 只做三件事 —— 把契约投递给执行者（派发）、把产出收回来（回写）、把证据留档（审计）；不承载任务数据、不做第二份任务源。

## 原型预览

原型为零依赖静态页面（原生 HTML / CSS / JS，无需构建），按真实集成语义实现交互；上下文注入与产物沉淀暂以数据字段示意。

```bash
# 方式一：本地起服务（推荐）
cd prototype && python3 -m http.server 8080
# 浏览器访问 http://localhost:8080

# 方式二：直接双击 index.html（file:// 亦可运行）
```

### 建议体验路径（5 分钟）

1. **任务驱动协作**：打开 `index.html?view=board&tenant=pay-settle`，点击业务信号横幅生成 PAY-2048 积压卡 —— 受理、卡片内澄清、确认任务契约后派发、人验收的完整演练；澄清未答复时任务不能进入待办或执行
2. **工作台 / 任务板**：待验收聚焦区 → 待办任务卡 → 详情抽屉 →「派发给 Agent」（选 Claude Code / Codex / OpenHands）
3. **会话台**：自动生成会话并模拟执行（终端输出 / 文件 diff / 测试结果）
4. **人验收**：任务自动停在「待验收」，详情抽屉「通过验收 → 已完成」或「打回」
5. **审计 / 成本 / 自动化**：全链路审计事件回看、模型成本按人 / 任务 / 模型归因、工作流实例审批放行续跑

七视图：`dashboard` · `board` · `sessions` · `automations` · `costs` · `audit` · `settings`

### 深链参数（评审直达）

```
?view=dashboard|board|sessions|automations|costs|audit|settings
?tenant=trade-core|pay-settle|platform
```

## 项目定位

**任务是团队与 Agent 之间的工作契约；项目是任务协作和经验积累的边界。** Tandem 把人的判断、Agent 的执行和项目的长期记忆，连接在同一个可追溯的工作流里。
