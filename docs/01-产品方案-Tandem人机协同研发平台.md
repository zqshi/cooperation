# Tandem（协动）人机协同研发平台产品方案

> 版本：v1.0｜日期：2026-10-22｜状态：评审稿

## 1. 产品摘要

Tandem 面向内网技术团队，将 Agent 作为默认执行者，把人的职责集中在任务规格、例外处理和最终验收。平台解决的不是“如何聊天或管理 Agent”，而是组织如何在 Agent 产出具有概率性的情况下，仍能获得可验收、可审计、可归因、可控成本的确定性交付，并让项目上下文持续复利。

产品判断：**项目是组织边界，任务是唯一工作单元；上下文是一等服务；产物是项目资产与上下文供给链。** 会话是任务的执行投影，事件是证据流，Agent 是可替换的履约方。

## 2. 调研与问题定义

### 2.1 调研范围与方法

本方案基于存量设计原点、开源组合评估、流程/需求基线、原型及 `ks-clawmate` 中的 agent-center、knowledge-service、runtime-conductor 文档进行案头研究；采用领域拆解、竞品能力矩阵、风险验证和端到端任务走查。外部开源版本、许可证和性能数据在 Phase 0 需重新核验，不把存量文档中的快照数字当作承诺。

### 2.2 用户与场景

| 用户 | 主要任务 | 当前痛点 | 成功结果 |
|---|---|---|---|
| 研发负责人 | 分派、看进度、控成本 | Agent 产出不可比较，失败难追责 | 任务级账本、证据和成本一屏可查 |
| 执行工程师 | 写清需求、处理例外、验收 | 反复解释上下文，验收材料不完整 | DoR 模板、证据包、可回退返工 |
| Agent/自动化 | 认领并完成可执行任务 | 绑定单一 Agent，权限和状态边界不清 | ACP 可插拔、任务元数据统一、只能到待验收 |
| 平台/安全管理员 | 租户、权限、审计 | 多系统日志割裂，越权风险 | 实例隔离、统一审计、预算熔断 |

### 2.3 核心问题

1. 任务意图、验收标准和执行现场分散，交付责任无法闭合。
2. Agent 失败、跑偏、超预算是常态，缺少证据门、重试和人验收。
3. 项目资料无法按任务检索，知识库越积越多却没有复利度量。
4. Agent 会更换，若依赖会话或厂商私有机制，平台能力会随代际失效。

## 3. 产品目标与边界

### 3.1 目标（试点 90 天）

- 让一条任务完整走通：信号→受理→DoR→Agent 执行→证据→人验收→完成。
- 让每个完成任务可回答：谁负责、谁执行、依据什么、花了多少、谁确认。
- 让上下文按任务拉取、可治理、可度量；未确认内容默认不进入稳定注入层。
- 让执行者可替换，任务状态和归因跨 Agent 保持不变。

### 3.2 非目标

不自研通用 Agent IDE；不建立第二任务源；不把知识库变成工作驱动源；不允许 Agent 直接完成任务；Phase 1 不承诺通用跨天编排和完全自动发布。

## 4. 产品原则与核心模型

### 4.1 四条硬规则

1. 项目承载目标、成员、任务板和共享资产；任务是唯一权威工作单元，承载意图、验收、预算和责任。
2. DoR 确认“可执行”，验收门确认“可交付”；二者均须留痕。
3. Agent 最多推进到 `in_review`，`done` 只能由授权人员确认。
4. 上下文是任务拉取型服务；任务产物登记到项目后，经权限、来源、版本和质量治理才能被后续任务引用。

### 4.2 状态与责任

采用七态：`backlog`（积压）、`todo`（待办）、`in_progress`（进行中）、`in_review`（审核中）、`blocked`（已阻塞）、`done`（完成）、`canceled`（已取消）。业务信号生成积压卡，受理并完成 DoR 后进入待办；审核驳回填写理由并回到进行中，保留同一卡片与历史 attempt；进行中可阻塞，解除后继续；取消后可重开到待办。进行中不能直接完成，每次状态变化产生审计事件。

### 4.3 双回路

任务回路回答“这次交付是否成立”；上下文回路回答“下次是否更容易成立”。任务是上下文唯一证据来源，验收结果反哺上下文质量标签。

## 5. MVP 产品范围

| 能力域 | MVP 交付 | 验收口径 |
|---|---|---|
| 信号受理 | webhook/人工录入、相似任务、范围和风险判断 | 受理建议可追溯，人工确认后创建任务 |
| 任务与项目 | 项目容器、成员与访问边界、任务板、DoR、父子任务、验收人 | 任务归属项目；未通过 DoR 不进入认领队列 |
| 执行调度 | 原子租约、Agent 路由、上下文包注入、心跳和超时 | 同一任务不重复执行，task/tenant 元数据贯穿 |
| 证据与验收 | commit、diff hash、CI、摘要、会话链接 | 最小证据不齐不能进 `in_review` |
| 上下文服务 | 稳定/经验/任务层、检索、审批、版本、命中度量 | 未确认条目不注入稳定层 |
| 项目产物 | 项目资产列表、来源任务、版本、摘要、索引、引用、权限 | 验收后登记；代码不复制，只保存 URI 和可引用元数据 |
| 治理 | SSO、实例级租户隔离、预算、审计、通知 | 按任务查全链路和成本 |

## 6. 关键流程与体验

### 6.1 创建到派发

受理人查看信号、相似历史和风险→确认任务契约→完成 DoR→调度器获取任务级 Context Pack→创建 ACP 会话→回写 `in_progress`。用户始终能看到任务、验收标准、上下文引用及适用于当前项目的治理信息。

### 6.2 执行到验收

会话结束后回写器校验证据，登记 Artifact，提交 Context Proposal，并将任务置为 `in_review`；通知验收人。验收人可通过、打回并填写理由，或阻塞并升级；不得自动通过。

### 6.3 澄清与项目资产复利

信号不完整时，接入层先创建项目内 `backlog` 卡片。受理人可在卡片提出澄清问题、指定补充方并记录回复；澄清期间状态保持 `backlog`，不进入认领队列。信息齐备后团队确认目标、范围、验收口径及执行约束，通过 DoR 转入 `todo`。

项目是任务组织和资产复用的粒度：看板聚合项目任务，项目资产区汇总人工上传与任务执行生成的产物。完成任务后，Agent 输出、测试/评审报告、决策记录等先关联来源任务并登记到项目；审核来源、权限、版本和质量后，再由 Context Service 按项目和当前任务检索注入。验收结果、返工原因、引用与采纳情况作为质量信号，帮助团队持续筛选有效经验；未经审核的产物不自动成为可信上下文。

### 6.3 返工与失败

打回反馈生成下一次执行契约；租约超时释放任务并允许换 Agent。预算上限、熔断与人工升级策略由项目治理配置决定。所有重试关联同一 `task_id` 和 attempt 序号。

## 7. 指标与试点门槛

核心指标：一次验收通过率、验收延迟 P50/P90、人时/任务、Agent 自动派发率、上下文命中率、上下文注入 token、失败重试率、预算超限率、审计完整率。Phase 0 只建立基线；Phase 1 要求审计完整率 100%、Agent 直接置 `done` 为 0、重复认领为 0，并观察一次通过率和人时/任务趋势改善。

## 8. 研究结论、取舍与风险

采用 dashi-taskboard 作为任务源、OpenHands Agent Canvas/Server 作为执行面、LiteLLM/Langfuse 做预算和 trace；Context/Artifact 自研。该组合的开源覆盖度只适用于任务/执行/治理/自动化主链路，不能表述为完整平台覆盖度。许可证、上游活跃度、多租户能力、提示注入防护和资源基线必须在 Phase 0 做实测。

主要风险：任务源维护者单一、执行面原生鉴权/租户能力不足、跨系统事件不一致、上下文污染、成本不可控。缓解措施为内部镜像与契约测试、认证网关和网络策略、幂等事件、分层审批、预算熔断及最小权限。

## 9. 分期路线

| 阶段 | 交付 |
|---|---|
| Phase 0（3 周） | 单仓库、单信号源跑通完整闭环，核验开源版本/API/许可证和资源 |
| Phase 1（6–8 周） | 两团队内网试点，SSO、Context/Artifact v1、审计成本、Automations |
| Phase 2（6–8 周） | Temporal 跨天流程、信任分级、多 Agent 路由、上下文过期回滚 |
| Phase 3 | 技能/评测闭环、跨项目复用、容量和成本优化 |

## 10. 待评审决策

任务源是否接受 dashi 的维护和多租户风险；首批试点团队与任务类型；高风险任务的人工审批级别；上下文稳定层审批角色；Phase 2 引入 Temporal 的触发阈值。以上决策完成前，方案中的组件版本、资源和工期均为假设。
