# Tandem 用户场景故事：从模糊信号到团队交付

> 用途：团队共识、产品评审、技术联调和试点演练  
> 版本：v1.1｜日期：2026-10-22

> 可交互演示：[`prototype/index.html?view=board&tenant=pay-settle&task=PAY-2048`](../prototype/index.html?view=board&tenant=pay-settle&task=PAY-2048)。演示从任务板信号进入采集区，人工确认收录后创建积压卡，并在统一会话台完成澄清、受理、任务契约确认和后续协作。

## 场景背景

支付结算团队收到一条退款结算相关反馈，但初始信息不足以确定具体问题、影响范围和预期结果。平台不能替团队补造业务规则，也不能把不完整信号直接派给 Agent。团队需要在项目任务板上共同补齐事实，再决定是否受理并进入执行。

参与者：林琳负责信号受理，周明负责任务范围和执行准备，陈工负责验收；Agent 可在 backlog 阶段协助澄清，在任务契约明确后才能执行编码任务，平台记录协作过程与产物。当前用户在同一工作台完成操作，所有动作写入审计。

## 一、信号先进入项目积压

林琳从项目任务板上的业务信号进入采集区，补齐收录信息并确认项目范围，人工确认后才创建 PAY-2048 `backlog` 卡。收录表示团队接手澄清，不代表通过 DoR 或批准执行。

初始卡片只描述已知事实：

```text
标题：处理退款结算反馈
来源：业务反馈
当前状态：backlog
待明确：问题表现、影响范围、期望结果及验收方式
```

## 二、卡片按来源进入不同澄清路径

### 路径 A：外部反馈卡片

PAY-2048 的原始反馈来自外部业务系统，即使由平台接入层建卡，来源仍标记为 `external`。林琳点击「来源系统 SDK」，打开绑定 PAY-2048 的统一会话台；头部展示来源系统与外部记录。发送留言后等待来源方反馈，结论保持待负责人确认。

外部来源通过来源系统 SDK 对话留言，等待来源方反馈。平台创建任务由模拟 Agent 多轮澄清，只整理已提供事实，不执行编码。两条路径均须负责人确认问题解决并在会话台确认 DoR，才可进入待办。

### 路径 B：平台创建卡片

周明在平台内新建一张独立的退款结算任务卡，来源为 `platform`，点击「与 Agent 澄清」。Agent 先复述已有意图，读取获准项目资料，再询问影响范围、期望结果和验收依据；周明回答后，Agent 展示更新的契约草稿及尚未解决的问题。此过程不预置结算规则，演示中的具体答复由参与者填写。

资料充分时 Agent 直接给出草稿，用户可修订或否定。业务事实需要他人确认时可邀请相关责任人补充，不能让 Agent 编造答案。澄清 Agent 此时不能启动编码、取得执行租约或宣布任务就绪。

### 两条路径共用的确认过程

澄清期间任务保持 `backlog`。问题收到答复后进入「待确认」，负责人确认充分后才标为「已解决」；无关问题需注明关闭理由。不完整或矛盾的答复继续追问，不能因收到回复而直接解锁执行。来源、对话历史、答复依据和确认结论始终保留在同一任务下。

## 三、确认任务契约并进入待办

周明在会话台右侧逐项确认：目标与范围已明确、验收标准已确认、依赖风险及执行约束已记录。确认前，任何未解决且未注明理由关闭的必要澄清项都会阻止任务契约完成。条件满足后，周明确认任务契约，卡片由 `backlog` 转入 `todo`。

实际规则、样例、测试方式、预算、代码变更方式和发布要求均由团队根据项目事实填写，不由平台预置为本故事的既定条件。

## 四、准备项目上下文并执行

团队按项目和任务范围选择相关资料。Context 服务返回带来源、版本和权限的引用；负责人检查上下文后再允许执行。Agent 获得任务契约和获准引用，完成团队明确的工作并提交摘要、变更引用及可用的验证证据。执行过程中遇到缺失信息或新风险时，团队可暂停并在任务中继续协商。

## 五、团队验收与返工

执行完成后任务进入 `in_review`。陈工依据这张任务卡上已确认的验收标准检查结果。若需要修改，陈工在卡片说明具体差距，任务回到执行流程并保留此前 attempt 与证据；若结果符合标准，由陈工确认完成。Agent 不代替团队作出验收决定。

## 六、产物沉淀到项目

任务完成后，团队可把有复用价值的摘要、决策或资料引用登记到所属项目资产。系统保留来源任务、版本、权限和审核状态。只有经过适当治理的内容才可进入后续任务检索；单次任务产物不会自动变成可信规则。

## 团队讨论

1. 哪些事实必须在澄清阶段获得，才能判断是否受理？
2. 谁负责答复问题，超时或无法答复时如何处理？
3. 哪些字段构成团队通用的最小任务契约，哪些应由项目自定义？
4. 什么类型的任务产物值得沉淀为项目资产，审核责任归谁？
5. 团队如何发现已沉淀资料过期、不准确或不再适用？

## 演示验收

- 信号与平台新意图先采集；必填信息及范围确认齐备后，人为确认生成 `backlog` 卡片。
外部来源通过来源系统 SDK 对话留言，等待来源方反馈。平台创建任务由模拟 Agent 多轮澄清，只整理已提供事实，不执行编码。两条路径均须负责人确认问题解决并在会话台确认 DoR，才可进入待办。
- 平台创建卡片展示「与 Agent 澄清」，演练追问、用户回答、契约草稿修订和人工确认。
- 澄清 Agent 在 `backlog` 可参与；此时不能编码或启动执行 attempt。
- 必要问题未解决时，即使已有答复也不能确认契约、进入 `todo` 或派发执行；来源不明时先确认来源。
- 切换辅助沟通方式不改写来源；关闭并重新打开面板可接续同一任务历史。
- 契约发生实质变化时撤销就绪确认；执行中出现关键缺口时暂停并进入 `blocked`。
- 澄清完成后，负责人确认通用任务契约，任务进入 `todo`。
- 协作、执行、验收和产物登记围绕同一任务及所属项目展开。

## 与正式方案的关系

本故事展示信号澄清、项目任务协作和资产复用的用户旅程，不定义结算业务规则。产品范围以《01-产品方案-Tandem人机协同研发平台》为准；接口、数据模型和权限以《02-技术设计-Tandem平台》为准。

## 收录门与原型能力边界

信号与平台新建意图首先进入采集区，采集区不是任务状态，不属于八态任务板。收录必填项目、原始来源、标题、问题或目标描述、联系人/责任人以及项目范围确认；`external` 另需来源引用。缺项提示且不建卡，人为创建可选 `backlog` 或 `confirming`；待办意向实际先进入 `confirming`，不能默认就绪。收录门确认是否纳入项目，DoR 确认可执行，两者分开。

问题、答复与历史、契约草稿和 DoR 保存于各任务对象。答复进入待确认，负责人确认解决后才允许通过 DoR 进入 `todo`；拖拽与派发也校验同一门禁。执行、返工和人工验收沿用现有模拟故事；操作统一记录为当前用户。`prototype/smoke-test.html` 覆盖缺项不建卡、收录后 backlog、两类来源路由、答复待确认阻塞、任务隔离和状态门，并保留原执行验收回归。

### 统一会话台与双层生命周期（交互模拟）

卡片的「打开 / 继续对话」跳转会话台并选中关联线程，不再打开澄清弹窗。左侧按全部 / Agent澄清 / SDK沟通 / 执行筛选，可叠加状态筛选；中间共享任务、阶段、会话状态、时间线和固定输入区；右侧提供问题确认、负责人 DoR、上下文确认、派发、暂停并澄清、恢复、人工验收 / 返工、取消 / 重开及查看任务。执行保留终端、diff 和证据；澄清复用消息、草稿与上下文。

任务采用八态：收录 `backlog` → 显式开始澄清 `confirming`（平台 Agent / 外部 SDK 共用）→ 必要问题解决并由负责人确认 DoR 后 `todo` → 唯一运行轮次 `in_progress` → 证据齐全 `in_review` → 授权人工 `done`。返工必须给理由，回待办后派发新轮次并保留历史；执行缺口暂停进入 `blocked`，旧计时停止，补齐并重新确认后回待办，通过「恢复执行」创建新轮次。取消进入 `canceled` 并停止执行；完成 / 取消重开按执行条件进入积压或待办，禁止直接执行。拖拽、输入与直接派发遵循同一门禁，Agent 永远不能确认完成。

澄清会话独立流转：`active`（进行中）、`waiting_reply`（等待回复）、`awaiting_confirmation`（等待负责人确认）、`resolved`（已解决）、`closed`（已关闭）。执行会话为运行 / 暂停 / 完成 / 失败 / 关闭。SDK 留言发送后记录等待来源方反馈；回调去重并校验所属任务、轮次及关联留言，已结束线程与任务拒绝迟到回调。已解决线程只读，新补充须明确「重新澄清」开启下一轮，撤销 DoR；未执行任务回积压，旧轮次消息保留。仅查看历史不改变业务状态。

澄清保存在任务及历史轮次，通过带 `kind` 的独立投影与执行列表合并，不写入执行 `state.sessions`，不参与运行数和成本统计。重要操作记录 activity / audit。四种采集预设仍只填表，不跳过收录和执行条件。全部为单页面内存模拟，关闭与切换保留消息草稿，刷新恢复种子数据；未接入真实 Agent、SDK 送达、身份鉴权、分布式执行租约或持久化。
