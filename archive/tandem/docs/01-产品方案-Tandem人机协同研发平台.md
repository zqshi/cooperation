# Tandem（协动）人机协同研发平台产品方案

> 版本：v1.0｜日期：2026-10-22｜状态：评审稿

## 1. 产品摘要

Tandem 面向内网技术团队，将 Agent 作为默认执行者，把人的职责集中在任务规格、例外处理和最终验收。平台解决的不是“如何聊天或管理 Agent”，而是组织如何在 Agent 产出具有概率性的情况下，仍能获得可验收、可审计、可归因、可控成本的确定性交付，并让项目上下文持续复利。

产品判断：**项目是组织边界，任务是唯一工作单元；上下文是一等服务；产物是项目资产与上下文供给链。** 会话是任务的执行投影，事件是证据流，Agent 是可替换的履约方。

## 2. 调研与问题定义

### 2.1 调研范围与方法

本方案基于存量设计原点、开源组合评估、流程/需求基线、原型及 `ks-clawmate` 中的 agent-center、knowledge-service、runtime-conductor 文档进行案头研究；采用领域拆解、竞品能力矩阵、风险验证和端到端任务走查。外部开源版本、许可证和性能数据在 Phase 0 需重新核验，不把存量文档中的快照数字当作承诺。

### 2.2 用户与场景

| 用户 | 主要任务 | 当前痛点 | 成功结果 |
|---|---|---|---|
| 研发负责人 | 分派、看进度、控成本 | Agent 产出不可比较，失败难追责 | 任务级账本、证据和成本一屏可查 |
| 执行工程师 | 写清需求、处理例外、验收 | 反复解释上下文，验收材料不完整 | DoR 模板、证据包、可回退返工 |
| Agent/自动化 | 认领并完成可执行任务 | 绑定单一 Agent，权限和状态边界不清 | ACP 可插拔、任务元数据统一、只能到待验收 |
| 平台/安全管理员 | 租户、权限、审计 | 多系统日志割裂，越权风险 | 实例隔离、统一审计、预算熔断 |

### 2.3 核心问题

1. 任务意图、验收标准和执行现场分散，交付责任无法闭合。
2. Agent 失败、跑偏、超预算是常态，缺少证据门、重试和人验收。
3. 项目资料无法按任务检索，知识库越积越多却没有复利度量。
4. Agent 会更换，若依赖会话或厂商私有机制，平台能力会随代际失效。

## 3. 产品目标与边界

### 3.1 目标（试点 90 天）

- 让一条任务完整走通：信号→受理→DoR→Agent 执行→证据→人验收→完成。
- 让每个完成任务可回答：谁负责、谁执行、依据什么、花了多少、谁确认。
- 让上下文按任务拉取、可治理、可度量；未确认内容默认不进入稳定注入层。
- 让执行者可替换，任务状态和归因跨 Agent 保持不变。

### 3.2 非目标

不自研通用 Agent IDE；不建立第二任务源；不把知识库变成工作驱动源；不允许 Agent 直接完成任务；Phase 1 不承诺通用跨天编排和完全自动发布。

## 4. 产品原则与核心模型

### 4.1 四条硬规则

1. 项目承载目标、成员、任务板和共享资产；任务是唯一权威工作单元，承载意图、验收、预算和责任。
2. DoR 确认“可执行”，验收门确认“可交付”；二者均须留痕。
3. Agent 最多推进到 `in_review`，`done` 只能由授权人员确认。
4. 上下文是任务拉取型服务；任务产物登记到项目后，经权限、来源、版本和质量治理才能被后续任务引用。

### 4.2 状态与责任

采用八态：`backlog`（积压）、`confirming`（确认中）、`todo`（待办）、`in_progress`（进行中）、`in_review`（审核中）、`blocked`（已阻塞）、`done`（完成）、`canceled`（已取消）。业务信号与平台新意图先进入采集区（非任务状态），人工确认收录后生成 backlog 卡，完成澄清与 DoR 后进入待办；审核驳回填写理由并回到待办，保留同一卡片与历史 attempt；进行中可暂停进入阻塞，显式打开澄清后进入确认中，重新确认后派发新轮次；取消后可重开到待办。进行中不能直接完成，每次状态变化产生审计事件。

### 4.3 双回路

任务回路回答“这次交付是否成立”；上下文回路回答“下次是否更容易成立”。任务是上下文唯一证据来源，验收结果反哺上下文质量标签。

## 5. MVP 产品范围

| 能力域 | MVP 交付 | 验收口径 |
|---|---|---|
| 信号受理 | webhook/人工录入、相似任务、范围和风险判断 | 先在采集区补齐收录信息，人工确认才建 backlog 卡；收录决定可追溯，收录不等于 DoR 或批准执行 |
| 任务与项目 | 项目容器、成员与访问边界、任务板、DoR、父子任务、验收人 | 任务归属项目；未通过 DoR 不进入认领队列 |
| 执行调度 | 原子租约、Agent 路由、上下文包注入、心跳和超时 | 同一任务不重复执行，task/tenant 元数据贯穿 |
| 证据与验收 | commit、diff hash、CI、摘要、会话链接 | 最小证据不齐不能进 `in_review` |
| 上下文服务 | 稳定/经验/任务层、检索、审批、版本、命中度量 | 未确认条目不注入稳定层 |
| 项目产物 | 项目资产列表、来源任务、版本、摘要、索引、引用、权限 | 验收后登记；代码不复制，只保存 URI 和可引用元数据 |
| 治理 | SSO、实例级租户隔离、预算、审计、通知 | 按任务查全链路和成本 |

## 6. 关键流程与体验

### 6.1 创建到派发

受理人查看信号、相似历史和风险→确认任务契约→完成 DoR→调度器获取任务级 Context Pack→创建 ACP 会话→回写 `in_progress`。用户始终能看到任务、验收标准、上下文引用及适用于当前项目的治理信息。

### 6.2 执行到验收

会话结束后回写器校验证据，登记 Artifact，提交 Context Proposal，并将任务置为 `in_review`；通知验收人。验收人可通过、打回并填写理由，或阻塞并升级；不得自动通过。

### 6.3 按来源开展任务澄清

卡片形成后先识别原始业务来源，再选择默认沟通方式。任务详情固定展示来源、澄清进度、责任人和契约草稿；所有沟通绑定同一 `task_id`，重新打开可接续历史。

| 来源 | 默认入口与沟通对象 | 交互过程 |
|---|---|---|
| 外部系统 `external` | 「来源系统 SDK」：打开统一会话台，发送留言并等待来源回调 | 显示来源系统、外部记录与关联留言；负责人确认来源答复 |
| 平台创建 `platform` | 「与 Agent 澄清」：打开任务关联的 Agent 对话 | Agent 阅读已有任务与获准项目资料，提出关键问题；用户回答后持续修订目标、范围、验收标准及约束草稿 |

来源指原始业务来源，不是创建接口调用方。外部系统通过 webhook、导入或人工转录形成的卡片仍属外部来源；平台内由用户或 Agent 发起的新意图属于平台创建。来源系统、外部记录链接与原文引用单独保存；纠正来源需记录修改人及原因，不能因为切换沟通方式而改写来源。

外部来源通过来源系统 SDK 对话留言，等待来源方反馈。平台创建任务由模拟 Agent 多轮澄清，只整理已提供事实，不执行编码。两条路径均须负责人确认问题解决并在会话台确认 DoR，才可进入待办。

**平台创建的澄清体验**：Agent 先复述已知意图，区分已确认事实与假设，每轮集中询问影响范围或验收的关键缺口；已有资料足够时直接提出契约草稿，避免机械问答。草稿与待解决问题并列展示，用户可修改、补充或否定。Agent 无法获知的业务事实交由具名责任人确认，不以生成内容代替事实。

**仅保留两种沟通方式**：平台创建使用 Agent 对话，外部来源使用 SDK 对话；参与者与辅助整理不产生第三种沟通入口。两种对话的结论均回到来源任务，由负责人确认。

**澄清与执行分离**：`backlog` 允许启动澄清 Agent，按权限读取资料、提问和生成草稿；不取得执行租约、不创建编码执行 attempt、不修改代码或触发发布。通过 DoR 后才允许派发执行 Agent。两者可使用同一供应商，但会话目的、权限和成本分类独立，执行只接收已确认版本及获准引用。

**确认门槛**：澄清项采用「待答复→待确认→已解决」，答复不充分可退回待答复；不适用项由负责人注明理由后关闭。收到消息、Agent 总结或填写了全部字段，都不自动代表澄清完成。只有所有必要问题已解决或有理由关闭、受理已确认、目标与范围/验收标准/依赖及约束具备可执行性时，负责人才能确认契约版本并通过 DoR，使 `backlog` 转为 `todo`。无澄清项且资料充分的任务可直接确认。新增关键问题或实质修改契约会撤销就绪确认；尚未执行则退回 `backlog`，执行中则暂停并转 `blocked`，补齐后重新确认再恢复。无法答复或超时由负责人决定继续追问、升级或取消，不自动放行。

### 6.4 项目资产复利

项目是任务组织和资产复用的粒度：看板聚合项目任务，项目资产区汇总人工上传与任务执行生成的产物。完成任务后，Agent 输出、测试/评审报告、决策记录等先关联来源任务并登记到项目；审核来源、权限、版本和质量后，再由 Context Service 按项目和当前任务检索注入。验收结果、返工原因、引用与采纳情况作为质量信号，帮助团队持续筛选有效经验；未经审核的产物不自动成为可信上下文。

### 6.5 返工与失败

打回反馈生成下一次执行契约；租约超时释放任务并允许换 Agent。预算上限、熔断与人工升级策略由项目治理配置决定。所有重试关联同一 `task_id` 和 attempt 序号。

## 7. 指标与试点门槛

核心指标：一次验收通过率、验收延迟 P50/P90、人时/任务、Agent 自动派发率、上下文命中率、上下文注入 token、失败重试率、预算超限率、审计完整率。Phase 0 只建立基线；Phase 1 要求审计完整率 100%、Agent 直接置 `done` 为 0、重复认领为 0，并观察一次通过率和人时/任务趋势改善。

## 8. 研究结论、取舍与风险

采用 dashi-taskboard 作为任务源、OpenHands Agent Canvas/Server 作为执行面、LiteLLM/Langfuse 做预算和 trace；Context/Artifact 自研。该组合的开源覆盖度只适用于任务/执行/治理/自动化主链路，不能表述为完整平台覆盖度。许可证、上游活跃度、多租户能力、提示注入防护和资源基线必须在 Phase 0 做实测。

主要风险：任务源维护者单一、执行面原生鉴权/租户能力不足、跨系统事件不一致、上下文污染、成本不可控。缓解措施为内部镜像与契约测试、认证网关和网络策略、幂等事件、分层审批、预算熔断及最小权限。

## 9. 分期路线

| 阶段 | 交付 |
|---|---|
| Phase 0（3 周） | 单仓库、单信号源跑通完整闭环，核验开源版本/API/许可证和资源 |
| Phase 1（6–8 周） | 两团队内网试点，SSO、Context/Artifact v1、审计成本、Automations |
| Phase 2（6–8 周） | Temporal 跨天流程、信任分级、多 Agent 路由、上下文过期回滚 |
| Phase 3 | 技能/评测闭环、跨项目复用、容量和成本优化 |

## 10. 待评审决策

任务源是否接受 dashi 的维护和多租户风险；首批试点团队与任务类型；高风险任务的人工审批级别；上下文稳定层审批角色；Phase 2 引入 Temporal 的触发阈值。以上决策完成前，方案中的组件版本、资源和工期均为假设。

## 收录门与原型能力边界

信号与平台新建意图首先进入采集区，采集区不是任务状态，不属于八态任务板。收录必填项目、原始来源、标题、问题或目标描述、联系人/责任人以及项目范围确认；`external` 另需来源引用。缺项提示且不建卡，人为创建可选 `backlog` 或 `confirming`；待办意向实际先进入 `confirming`，不能默认就绪。收录门确认是否纳入项目，DoR 确认可执行，两者分开。

问题、答复与历史、契约草稿和 DoR 保存于各任务对象。答复进入待确认，负责人确认解决后才允许通过 DoR 进入 `todo`；拖拽与派发也校验同一门禁。执行、返工和人工验收沿用现有模拟故事；操作统一记录为当前用户。`prototype/smoke-test.html` 覆盖缺项不建卡、收录后 backlog、两类来源路由、答复待确认阻塞、任务隔离和状态门，并保留原执行验收回归。

### 统一会话台与双层生命周期（交互模拟）

卡片的「打开 / 继续对话」跳转会话台并选中关联线程，不再打开澄清弹窗。左侧按全部 / Agent澄清 / SDK沟通 / 执行筛选，可叠加状态筛选；中间共享任务、阶段、会话状态、时间线和固定输入区；右侧提供问题确认、负责人 DoR、上下文确认、派发、暂停并澄清、恢复、人工验收 / 返工、取消 / 重开及查看任务。执行保留终端、diff 和证据；澄清复用消息、草稿与上下文。

任务采用八态：收录 `backlog` → 显式开始澄清 `confirming`（平台 Agent / 外部 SDK 共用）→ 必要问题解决并由负责人确认 DoR 后 `todo` → 唯一运行轮次 `in_progress` → 证据齐全 `in_review` → 授权人工 `done`。返工必须给理由，回待办后派发新轮次并保留历史；执行缺口暂停进入 `blocked`，旧计时停止，补齐并重新确认后回待办，通过「恢复执行」创建新轮次。取消进入 `canceled` 并停止执行；完成 / 取消重开按执行条件进入积压或待办，禁止直接执行。拖拽、输入与直接派发遵循同一门禁，Agent 永远不能确认完成。

澄清会话独立流转：`active`（进行中）、`waiting_reply`（等待回复）、`awaiting_confirmation`（等待负责人确认）、`resolved`（已解决）、`closed`（已关闭）。执行会话为运行 / 暂停 / 完成 / 失败 / 关闭。SDK 留言发送后记录等待来源方反馈；回调去重并校验所属任务、轮次及关联留言，已结束线程与任务拒绝迟到回调。已解决线程只读，新补充须明确「重新澄清」开启下一轮，撤销 DoR；未执行任务回积压，旧轮次消息保留。仅查看历史不改变业务状态。

澄清保存在任务及历史轮次，通过带 `kind` 的独立投影与执行列表合并，不写入执行 `state.sessions`，不参与运行数和成本统计。重要操作记录 activity / audit。四种采集预设仍只填表，不跳过收录和执行条件。全部为单页面内存模拟，关闭与切换保留消息草稿，刷新恢复种子数据；未接入真实 Agent、SDK 送达、身份鉴权、分布式执行租约或持久化。
