# 项目定位：核心目标与一等公民（第一性原理分析）

> 版本：v1.2（2026-10-21）· v1.2 增加"一等服务"维度：任务仍是唯一一等公民，上下文升为一等服务
> 平台代号：**Tandem（协动）**
> 定位：本文是全部方案与实现文档的"设计原点"，回答三个奠基问题：① 平台的核心目标是什么？② 从第一性原理推导，哪些设计是必然？③ 平台的一等公民是什么、围绕什么构建？
> 后续文档（产品方案、技术设计、用户场景、架构图、流程时序图）与 `prototype/` 均以本文为设计约束。

---

## 1. 核心目标

### 1.1 先立前提，再破边界

- **前提：Agent 必须真把活干了。** 平台的默认生产路径是 Agent 执行（AI Native）——任务被派发、被认领、被执行，人退到规格、例外与验收三个位置；没有真实执行，后面的验收、审计、计量都失去对象。
- **不重复造 Agent 的能力。** "能不能写代码"是 Agent 厂商的迭代问题；平台不押注单一 Agent（A3），只负责把任务交给当下最合适的执行者。
- **不是"管理一堆 Agent"。** 那是工具视角，把手段当成了目的；平台管理的是任务契约，不是 Agent。

### 1.2 是什么（一句话）

> **前提是 Agent 在生产路径上真实执行；在此基础上，平台把 Agent 的概率性产出，转化成组织可信任、可验收、可审计、可计量的确定性交付——并在 Agent 世代更替中保持这一能力不贬值；同时让项目上下文持续沉淀，使同类任务越做越省。**

### 1.3 本质：信任机器（Trust Machine）

平台真正解决的是"**组织敢不敢把活交给 Agent**"：

- 不敢的根因不是能力，而是**不可验收、不可审计、成本不可控、失败不可回退**；
- 因此平台的每个功能都应能回答："它如何降低组织的信任门槛？"

## 2. 第一性原理推演

### 2.1 公理（领域内不可绕过的既定事实）

| # | 公理 | 说明 |
|---|---|---|
| A1 | **Agent 产出是概率性的** | 会失败、跑偏、超预算、卡住；能力真实，但可靠性是统计的，不是确定的 |
| A2 | **责任不可转移给机器** | "谁做的、何时、花了多少、依据什么、谁确认的"必须可回答（金融/交易语境尤甚） |
| A3 | **Agent 迭代快于平台迭代** | 主力 Agent 会更换（现实约束：团队主力未固定）；押注单一 Agent 的平台必然过期 |
| A4 | **组织的价值单元是"工作任务"而非"对话"** | 任务跨 Agent 生命周期存续；会话随执行生死 |
| A5 | **瓶颈是信任，不是能力** | 组织不敢用 Agent 的根本原因：不可验收 / 不可审计 / 成本不可控 / 失败不可回退 |

### 2.2 推导：设计必然

| 由公理 | 推导出的设计必然 | 已落地决策 |
|---|---|---|
| A1 + A2 | 强制人验收门：机器只能"建议完成"，人才能"宣布完成" | 铁律：Agent 不能置 `done`；`in_review` 验收门 |
| A1 + A5 | 证据链（diff/测试/摘要）+ 可重派 + 可回退 + 预算熔断 | 会话产出回写；打回重做；LiteLLM budget 熔断 |
| A3 | 执行者必须可插拔，平台对 Agent 保持中立 | ACP 多 Agent；taskctl 协议化；不依赖单一 Agent 私有机制 |
| A4 + A2 | 需要一个稳定锚点承载归因、验收、计量 | 任务为唯一权威源；`task_id` 注入 metadata |
| A5 | 全链路可观测 | 审计多源归一（任务/会话/Git/上下文/产物）；成本按任务归因；通知到人 |
| A1 + A5（叠加复利目标） | 上下文必须可治理、按任务检索、可度量，且默认不自动入库 | Context Service 分层审批；任务级注入 + token 预算；命中率与一次通过率趋势 |

## 3. 一等公民：任务（Task）

### 3.1 判定标准（四问）

1. 是否承载平台的不变量（验收门 / 归因 / 预算 / 租户边界）？
2. 生命周期是否跨越 Agent 世代？
3. 删除它，平台是否归零？
4. 是否是组织记账的最小单元？

### 3.2 判定结果

| 测试 | 任务 | 会话 | 上下文 | 事件 |
|---|---|---|---|---|
| 承载平台不变量（验收门/归因/预算/租户边界） | ✅ 全部 | ❌ | ❌ 无验收、无责任 | ❌ |
| 跨 Agent 世代存续 | ✅ 永续 | ❌ 易逝 | ✅ 仅作为资源 | ✅ 仅记录 |
| 删除后平台是否归零 | ✅ 归零 | ❌ 重派即可 | ❌ 变笨，不失责 | ❌ 只丢证据 |
| 组织记账的最小单元 | ✅ | ❌ | ❌ | ❌ |

**结论：任务是唯一一等公民，其本质是"人机之间的执行契约"。**

上下文不满足公民条件，但满足"必须独立建设"的服务条件——因此它是**一等服务**，不是一等公民。这个区分见 §3.5。

### 3.3 契约语义（核心关系）

- **任务 = 契约**：意图 + 验收标准 + 计量单位；唯一权威源。
- **会话 = 契约的执行态投影**：可 0..n 次、可替换、可失败——"雇佣的临时工"，不是公民。
- **事件 = 契约的证据流**：审计 / 成本 / 时间线均为其派生视图（projection）。
- **Agent = 可替换的履约方**：平台对其中立；Agent 甚至可以不应感知平台存在（通过 CLI/Skill 操作任务）。

### 3.4 回看既定决策（自检）

- **dashi-taskboard 的验收门为什么可用（但需复核执法点）**：它提供了 `in_review` 的人验收位；但其"Agent 不得置 done"目前是 Skill 层约定而非服务端强制——因此 Tandem 必须把这条规则在适配层授权模型中强制执行，不能依赖上游自觉；
- **OpenHands 为什么不能直接当平台**：其世界观里**会话是一等公民**——会话不进组织账本、不跨 Agent 存续、无法承载验收与归因；
- **薄适配层为什么薄**：只做三件事——把契约投递给执行者（派发）、把产出收回来（回写）、把证据留档（审计）；不承载任务数据、不做第二份任务源；上下文检索与产物登记不在薄层实现，而是调用 Context（一等服务）与 Artifact（支撑服务）；
- **多租户 = 契约账本的隔离边界**；**成本 = 契约的资源计量**；**审计 = 契约的操作日志**——全部挂在任务上。

### 3.5 一等服务：上下文（产物为供给链）

**判定标准（与公民四问分开）：**

1. 是否承载平台的复利能力（同类任务越做越省）？
2. 是否直接闭合"沉淀 → 检索 → 注入 → 度量"的复利回路？
3. 是否需要独立 API、存储、治理、SLO 与度量？
4. 是否被任务拉取，而不是驱动任务？
5. 删除它，平台是否只是变慢/变笨，而不失去责任与账本？

上下文五条全中 → **一等服务**。产物只提供可检索材料，不直接闭合复利回路，因此是**支撑服务**（上下文供给链），不称一等。

**为什么上下文不能升为公民：**

- 没有验收：上下文不能被"完成"，只能被确认、过期、废弃；
- 没有责任：出错时无法追责到某条上下文，只能追责到采纳它的人与任务；
- 没有独立账本：它的价值由任务结果（一次通过率、人时/任务）定义；
- 派生性：没有任务/会话/产物，上下文就没有证据来源。

若把上下文升为公民，会重演"会话中心主义"，变成"知识库中心主义"：资料越堆越多，却无人对交付负责。

**双回路：**

```
任务回路（时钟/账本）
信号 → 任务 → 认领 → 执行 → 证据 → 验收 → 完成
回答：这次交付是否成立

上下文回路（记忆/复利）
任务/会话/产物 → 提议 → 治理 → 存储 → 检索 → 注入 → 度量
回答：下次交付是否更容易成立
```

咬合点：

- 任务是上下文唯一的证据来源；
- 上下文是任务的输入（按任务检索，不遍历全量）；
- 验收结果是上下文质量的标签（通过/打回原因反哺治理）。

**方向约束：上下文是任务拉取型服务，不是任务驱动源。** 任务按需拉取上下文；上下文不主动"推"工作。否则平台会滑向知识管理产品。

**边界：**

| 维度 | 任务 | 上下文 |
|---|---|---|
| 生命周期 | 状态机与验收 | 确认/过期/废弃，无 done |
| 权威 | 唯一权威源 | 引用任务/会话/产物，不反向承载任务状态 |
| 责任 | 人签字 | 人审批（按层分级） |
| 度量 | 人时/任务、一次通过率、验收延迟 | 命中率、token 成本、重复理解时间 |
| 删除影响 | 平台归零 | 变慢、变笨，但不失责 |

**产物（Artifact）**：代码在仓库；执行交付物与项目资料中可被大模型引用的部分，登记为产物，进入上下文供给链。产物服务不复制代码，只做登记、摘要、索引、引用与权限。

## 4. 平台围绕什么构建

### 4.1 核心：任务契约的完整生命周期 × 三处"责任转移点"

1. **创建 → 派发**：人的意图变成 Agent 的契约（派发器向上下文服务发起任务级检索，组装上下文包 + 注入 `task_id` metadata）；
2. **执行 → in_review**：Agent 的产出变成人的待办（回写器 + 证据摘要 + 通知；同时生成上下文提议与产物登记）；
3. **验收 → done / 打回**：人的判断结账，或生成新契约（验收门 + 反馈回路闭环；验收结果成为上下文质量标签）。

> 三处转移点分别对应上下文回路的三个动作：**拉取、沉淀、校准**。

### 4.2 配套功能归属（全部是转移点的配套设施）

| 功能 | 归属 |
|---|---|
| 信号接入与受理 | 契约的候选来源与准入判断（积压队列 → 任务） |
| 上下文服务 | 契约的按任务检索与注入（任务拉取型，不驱动任务） |
| 产物服务 | 契约交付物与项目资料的登记、索引与引用（上下文供给） |
| 自动化（Automations / Temporal） | 契约的自动签发与跨天流转 |
| 成本治理（LiteLLM / Langfuse） | 契约的预算条款与资源计量 |
| 审计中心 | 契约的操作日志（证据流查询视图） |
| 多租户 | 契约账本的隔离边界 |
| 通知 | 转移点触发的人侧提醒 |

### 4.3 设计第一问（准入规则）

> 新功能评审第一问：**它挂在任务生命周期的哪个转移点上？** 答不上来的，不进 Phase 1。
>
> 对知识/记忆/产物类功能追加第二问：**它是否让同类任务的下一次交付更省人时？** 两问皆否，不进 Phase 1。

### 4.4 类比：把"工程外包"制度化

- 任务 = 工作说明书（SOW）；会话 = 施工队（随时可换）；验收 = 验收单；审计 = 监理记录；预算 = 合同限额。
- 制度的核心不是施工队，而是**"委托—验收"契约**——这也正是本平台与"Agent 工具"的根本区别。

## 5. 反模式清单（违反一等公民的典型错误）

- **会话中心主义**：以会话/对话为主界面组织一切 → 换 Agent 即断代，组织账本对不上；
- **知识库中心主义**：以文档/知识库为主界面组织一切 → 资料越堆越多，却无人对交付负责；上下文只能作为任务拉取的服务；
- **上下文自动写入**：Agent 产物未经治理直接进入稳定层/决策层 → 污染复利，越做越笨；
- **上下文=全量注入**：每次把项目资料全部塞给模型 → token 成本失控，关键信息被淹没；必须按任务检索并设预算；
- **Agent 私有归因**：依赖某 Agent 的私有机制（如专属线程 ID / 专属 Skill）→ 违背 A3 可插拔公理；
- **第二任务源**：薄适配层或外部工具里再存一份任务状态 → 违背"唯一权威源"，账目分裂；
- **把 done 交给机器**：任何"自动完成 / 自动合并"捷径 → 违背 A2 责任公理；
- **功能不落转移点**：无法归属三处转移点的功能（纯装饰面板等）不进 Phase 1。

---

## 6. 结论

- 平台的默认生产路径是 Agent 执行，但它不是围绕"Agent 本身"构建的（Agent 只是可替换的履约方），也不是围绕"看板"构建的；
- 它围绕**任务契约的完整生命周期**构建：会话、事件、成本、审计、自动化都是契约的附属投影；
- **任务是一等公民，上下文是一等服务**：任务决定"这次交付是否成立"，上下文决定"下次交付是否更容易成立"；
- 一切设计评审以本文公理（§2.1）、准入规则（§4.3）与一等服务边界（§3.5）为准。
