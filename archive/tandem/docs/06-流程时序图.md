# Tandem 流程时序图

> 版本：v1.0（2026-10）
> 范围：Phase 1 核心流程的端到端时序，覆盖信号受理、任务执行、上下文治理、打回返工、异常重试、预算熔断与双 Agent 评审。
> 配套：`docs/05-产品架构图.md`（分层与域模型）、`docs/02-技术设计-Tandem平台.md`（实现细节）、`docs/03-用户场景故事-一次结算规则变更.md`（协同演练）。
> 图表格式：Mermaid `sequenceDiagram`，GitHub / IDE 可直接渲染。

---

## 0. 读图约定

- 所有时序均使用 `autonumber`，编号只用于阅读，不是接口序号；
- `alt / else` 表示分支，`opt` 表示可选步骤，`Note` 表示约束说明；
- 任务状态以任务源为准；上下文条目状态以 Context Service 为准；
- 图中“人”默认是具名责任人，不是抽象角色；Agent 不得代替人做验收或完成决定。

### 0.1 参与者

| 代号 | 参与者 | 职责 |
|---|---|---|
| 信号源 | Jira / IM / 邮件 / 监控 / 人工录入 | 产生原始信号 |
| 接入层 | 信号适配、去重、归一、Triage | 把信号变成候选任务 |
| 任务源 | dashi-taskboard | 唯一任务权威源、状态机、验收门 |
| 调度器 | 认领、租约、派发、回写 | 连接任务与执行面 |
| 执行人 / Agent | 人、OpenHands、ACP Agent | 实际执行并提交证据 |
| Context Service | 上下文服务（一等） | 捕获、治理、检索、注入、度量 |
| Artifact Service | 产物服务（支撑） | 登记、摘要、索引、引用 |
| 验收人 | 任务验收责任人 | 通过 / 打回，唯一完成权 |
| 审计 | 审计聚合 | 不可篡改记录关键事件 |
| 通知 | IM / 邮件 / 站内信 | 待办、超时、异常提醒 |

### 0.2 流程总览

| 编号 | 流程 | 触发 | 结束状态 |
|---|---|---|---|
| S1 | 信号受理与任务创建 | 新信号进入采集区，人工确认收录后进入积压队列 | `backlog` |
| S2 | 任务认领、执行与验收 | 任务满足 DoR | `in_review` / `done` / `in_progress` / `blocked` |
| S3 | 上下文沉淀与治理 | 会话产出证据 | 条目 `active` 或 `rejected` |
| S4 | 打回与返工 | 验收不通过 | `in_progress` / `blocked` |
| S5 | 租约超时、失败与重试 | 心跳超时 / 会话失败 | `in_progress` / `blocked` |
| S6 | 预算熔断 | 任务成本超限 | `blocked(budget_blocked)` |
| S7 | 双 Agent 评审（可选） | 执行完成、需交叉审查 | 仍为 `in_review` |

## 1. S1 信号受理与任务创建

**前置条件**：信号已进入接入层；项目范围与受理标准已配置。
**后置条件**：新信号先完成收录门，经人工确认生成已收录的 `backlog` 卡片；受理、补充信息、拒绝或合并均在同一卡片留痕。

```mermaid
sequenceDiagram
  autonumber
  participant S as 信号源
  participant I as 信号接入
  participant D as 去重/归一
  participant R as 受理 Triage
  participant H as 受理人
  participant L as LLM 辅助
  participant T as 任务源 dashi
  participant A as 审计

  S->>I: 推送或拉取原始信号
  I->>D: 归一化 source / external_id / fingerprint
  D-->>I: 新信号、重复或合并候选
  alt 重复或可合并
    I->>A: signal.deduped
    I-->>S: 忽略或关联已有任务
  else 新信号
    I-->>H: 展示候选信号，补齐最小收录信息
    H->>I: 填写项目、来源、目标、责任人及来源引用，确认项目范围
    I->>I: 校验必填字段（缺项则提示、不建卡）
    H->>I: 确认并加入积压
    I->>T: 校验通过且人为确认后创建 backlog 卡片
    T-->>R: task_id + 信号来源
    R->>A: signal.received
    alt 人工受理
      R->>H: 展示信号、项目范围、相似历史
      H->>R: accept / reject / needs_info / merge
    else LLM 辅助
      R->>L: 按配置标准评估
      L-->>R: 建议 + 置信度 + 理由
      R->>H: 建议与理由（默认需确认）
      H->>R: 确认或修改
    end
    alt accept
      R->>T: 确认受理（保持 backlog）
      T-->>R: task_id
      R->>A: triage.decided
      R-->>H: 任务进入积压卡（backlog）
    else reject / needs_info / merge
      R->>A: triage.decided
      R->>T: 拒绝则 canceled；补信息保持 backlog；合并则关联已有卡并取消重复卡
      R-->>S: 反馈决定与任务链接
    end
  end
```

**关键规则**

1. 新信号去重后进入采集区，字段缺失只提示、不建卡；人为确认收录后生成 `backlog` 积压卡，不另建第二张任务卡。
2. `backlog` 需受理并通过 DoR 才进入 `todo`；DoR 是准入字段，不新增 ready/draft 状态。
3. LLM 默认只给建议；低风险来源可在校准后自动受理，但必须保留 `reason` 与审计。
4. 受理 SLA 24h；超时进入升级队列，不允许无限期沉默。
5. 重复信号只做关联或合并，不重复建任务。

**异常分支**

| 场景 | 处理 |
|---|---|
| 重复信号 | 记录 `signal.deduped`，关联已有任务或忽略 |
| 信息不足 | 标记 `needs_info`，保持积压卡并请求来源补充 |
| 超出项目范围 | 拒绝并记录理由，可转其他项目 |
| LLM 置信度低 | 强制人工确认，不自动受理 |
| 任务源不可用 | 信号留在积压队列，重试；不双写其他任务源 |

### S1 补充：卡片形成后的来源分流

```mermaid
sequenceDiagram
  actor H as 任务负责人
  participant T as 任务卡与契约
  participant C as 任务对话
  participant A as 澄清 Agent
  H->>T: 打开 backlog 卡片
  alt external
    T-->>H: 来源系统 SDK 对话
    H->>C: 基于任务提问
    C-->>H: SDK 留言 / 带 messageId、replyTo 的来源回调
  else platform
    T-->>H: 与 Agent 澄清
    H->>A: 任务意图与获准资料
    A-->>H: 关键追问和契约草稿
    H->>A: 回答、修订、补充依据
  end
  H->>T: 确认必要问题已解决或附理由关闭
  H->>T: 确认契约版本与 DoR
  T->>T: 原子校验来源、受理、问题状态与契约
  T-->>H: 通过则 todo，否则保持 backlog
```

澄清会话不取得执行租约、不创建编码 attempt；外部对话采用 SDK 留言与来源回调。答复不等于问题解决，Agent 草稿不等于人工确认。切换辅助沟通方式不改写原始来源；契约实质变化使 DoR 失效，执行中先暂停并转 `blocked`，重新确认后才能恢复。

## 2. S2 任务认领、执行与验收

**前置条件**：任务为 `todo`，DoR 通过，预算与容量可用。
**后置条件**：证据齐全则 `in_review`，人验收后 `done` 或打回；证据不足则保持 `in_progress` 补齐，或进入 `blocked`。

```mermaid
sequenceDiagram
  autonumber
  actor H as 验收人
  participant E as 执行人/Agent
  participant SCH as 调度/认领服务
  participant TS as 任务源 dashi
  participant CS as Context Service
  participant OH as OpenHands
  participant SB as 沙箱/工作区
  participant CI as Git/CI
  participant AS as Artifact Service
  participant AU as 审计

  E->>SCH: POST /claims（task_id, executor_type）
  SCH->>TS: 校验 dor_state=ready / 状态 / 策略
  TS-->>SCH: 可认领
  SCH->>TS: 原子认领（lease, attempt+1）
  TS-->>SCH: claim_id / lease_expires_at
  SCH->>AU: claim.acquired
  SCH->>CS: GET /context/query(task_id, token_budget)
  CS-->>SCH: context_pack + citations

  alt Agent 执行
    SCH->>OH: 创建会话（context_pack + 验收标准）
    OH->>SB: 启动隔离工作区
    SB->>CI: 分支 / 提交 / PR / 测试
    CI-->>SB: 测试结果 / PR 链接
    SB-->>OH: 事件流 / diff / 日志
    OH-->>SCH: session.completed
  else 人工执行
    SCH-->>E: 返回 lease + context_pack
    E->>CI: 本地执行并提交 PR
    E->>SCH: session.completed（附证据）
  end

  SCH->>CI: 校验最小证据集
  alt 证据不足
    SCH->>TS: 保持 in_progress 补证据，或 blocked(evidence_missing)
    SCH->>AU: evidence.rejected
  else 证据齐全
    SCH->>AS: artifact.register（证据/文档）
    SCH->>CS: context.propose（pending）
    SCH->>TS: in_review + 摘要 + 证据链接
    TS->>AU: evidence.attached
    TS->>H: 通知待验收
  end

  alt 验收通过
    H->>TS: approve
    TS->>TS: done
    TS->>CS: quality label = accepted（按 context_usage 归因）
    TS->>AU: approval.grant
  else 打回
    H->>TS: reject + 反馈
    TS->>CS: quality label = rejected（按 context_usage 归因）
    TS->>AU: approval.reject
    TS-->>SCH: 回到 todo（契约失效时阻塞并补齐 DoR）
  end
```

**关键规则**

1. 首次、返工和重试均从 `todo` 认领，DoR 与上下文仍须满足；认领必须是原子操作，同一任务同时只有一条活动租约。
2. 先认领、后检索：`context.query` 必须带 `task_id` 与 token 预算，返回条目必须带引用。
3. `context_pack` 只包含 `active` 条目；`pending` 提议永不注入。
4. Agent 不得置 `done`、不得直推主干、不得 force push；只提交 PR 与证据。
5. 证据最小集不齐，不得进入 `in_review`；验收通过后由人关闭任务。
6. 验收结果回写上下文质量标签，供后续检索排序与治理。

**异常分支**

| 场景 | 处理 |
|---|---|
| 重复认领 | 租约 CAS 失败，返回 409；不产生第二个执行会话 |
| 上下文检索超时 | 默认降级为空 pack 并标记 `context_degraded`；高敏项目可配置阻断 |
| 上下文为空 | 允许执行，但标记 `context_miss`，用于后续补条目 |
| 会话失败 | 走 S5 失败/重试；不直接判任务失败 |
| 证据缺失 | 保持 `in_progress` 补证据，或进入 `blocked(evidence_missing)` |
| 验收人不在 | 任务保持 `in_review`，通知升级；不得自动通过 |

## 3. S3 上下文沉淀与治理

**前置条件**：任务已产出证据或可复用结论；提议人已完成来源标注。
**后置条件**：条目进入 `active` 或 `rejected`；只有 `active` 可被检索。

```mermaid
sequenceDiagram
  autonumber
  participant W as 回写服务
  participant AS as Artifact Service
  participant CS as Context Service
  participant R as 审批人
  participant DB as 上下文库
  participant AU as 审计

  W->>AS: 登记产物/证据（URI + 摘要 + 权限）
  AS->>AS: 敏感检查 + 切分 + 向量化
  AS-->>W: artifact_id

  W->>CS: context.propose（L2/L3, pending）
  CS->>CS: 去重 + 冲突检测
  alt 重复或冲突
    CS->>W: 合并建议或拒绝
    CS->>AU: context.deduped
  else 新提议
    CS->>R: 进入审批队列（来源/任务/证据）
    alt 确认
      R->>CS: confirm / edit
      CS->>DB: 写入新版本（active, expires_at）
      CS->>AU: context.confirm
    else 拒绝
      R->>CS: reject + reason
      CS->>AU: context.reject
    end
  end

  CS->>DB: 更新索引与引用
  Note over CS,DB: 只有 active 条目可检索；pending 永不注入
```

**关键规则**

1. L1 稳定层、L2 决策层、L3 经验层、L4 产物层分权治理；L3 默认人工确认。
2. 任何 Agent 提议默认 `pending`；不得自动进入 `active`。
3. 失败任务的结论不得进入 L1/L2；只可作为 L3 待审提议，并标注失败上下文。
4. 条目必须有来源、负责人、有效期、版本；支持过期、回滚、冲突检测。
5. 产物服务只登记 URI、摘要、索引与权限；代码正文留在 Git，不复制。
6. 上下文按租户/项目隔离；跨项目复用必须显式授权。

**异常分支**

| 场景 | 处理 |
|---|---|
| 提议重复 | 合并到已有条目，保留来源链接 |
| 与现有条目冲突 | 标记冲突，进入人工裁决；不覆盖旧版本 |
| 审批超时 | 条目保持 `pending`；不阻塞任务完成，但计入治理积压 |
| 来源任务被删除 | 条目降级或失效，保留审计链 |
| 敏感信息 | 阻断入库；进入安全评审，不进入检索索引 |

## 4. S4 打回与返工

**前置条件**：任务处于 `in_review`，验收人给出明确打回理由。
**后置条件**：任务回到 `todo`；重新派发后返工产生新会话与新证据。

```mermaid
sequenceDiagram
  autonumber
  actor H as 验收人
  participant TS as 任务源
  participant SCH as 调度/认领
  participant CS as Context Service
  participant OH as OpenHands
  participant AU as 审计

  H->>TS: reject + 反馈
  TS->>TS: 写入任务级反馈 + attempt 记录 + DoR 复核
  TS->>CS: 记录 quality label = rejected（不自动生成全局条目）
  TS->>AU: approval.reject

  alt DoR 仍满足
    TS->>TS: todo（等待派发返工）
  else DoR 失效
    TS->>TS: in_progress → blocked（补验收标准/范围，暂停派发）
  end

  SCH->>TS: 重新认领（新 attempt）
  TS-->>SCH: 任务级反馈
  SCH->>CS: query（仅全局 active 条目）
  CS-->>SCH: context_pack
  SCH->>OH: 新建修订会话（context_pack + 任务级反馈）
  OH-->>SCH: 新证据
  SCH->>TS: in_review
  TS->>H: 再次验收
```

**关键规则**

1. 每次返工必须新建会话，不复用旧会话；旧证据保留，不覆盖。
2. 打回反馈保存在任务源/会话记录，不自动升级为全局条目；如需沉淀，走 S3 审批。
3. 返工计入 `attempt` 与成本；超过上限转人工或拆分任务。
4. 打回必须给理由码与可操作反馈，否则验收操作无效。
5. DoR 失效时先补契约，不带着模糊标准反复返工。

**异常分支**

| 场景 | 处理 |
|---|---|
| 反馈为空 | 拒绝该次打回操作，要求填写理由码 |
| 连续返工超限 | 转人工处理或拆分为子任务，不无限重试 |
| 旧会话仍有租约 | 先释放旧租约，再创建新会话 |
| 任务范围变化 | 转为 `blocked` 重新复核 DoR，补齐确认后回 `todo`，派发后再进入执行；范围独立时拆分新积压卡 |

## 5. S5 租约超时、失败与重试

**前置条件**：任务处于 `in_progress`，存在活动租约或执行会话。
**后置条件**：可重试则保持 `in_progress` 并释放租约；不可重试则 `blocked`。

```mermaid
sequenceDiagram
  autonumber
  participant SCH as 调度器
  participant CL as 租约库
  participant OH as 执行会话
  participant TS as 任务源
  participant N as 通知
  participant AU as 审计

  alt 租约扫描
    SCH->>CL: 扫描过期租约（heartbeat > TTL）
    CL-->>SCH: 释放租约
    SCH->>AU: claim.expired
  else 会话失败
    OH-->>SCH: failed / timeout
  end

  SCH->>TS: 记录 reason_code
  alt 可重试且 attempt < 2
    SCH->>TS: 保持 in_progress，允许新 attempt 认领
    SCH->>N: 通知可认领（优先换 Agent）
  else 不可重试或超限
    SCH->>TS: blocked(reason_code)
    SCH->>N: 转人工队列
  end
```

**关键规则**

1. 租约必须有 TTL 与心跳；超时自动释放，避免任务被永久占用。
2. 重试上限默认 2 次；每次重试优先换执行者，避免同一 Agent 重复失败。
3. 失败必须记录 `reason_code`，不允许只写“失败”两个字。
4. 不可重试错误直接 `blocked`，转人工；不得静默丢弃。
5. 租约释放与重新认领必须幂等，避免并发重复执行。

**异常分支**

| 场景 | 处理 |
|---|---|
| 心跳丢失但会话仍在跑 | 先标记租约过期，再终止/回收会话，防止双写 |
| 执行者主动放弃 | 释放租约，保持 `in_progress` 等待重新认领，记录 `abandoned` |
| 连续失败 | `blocked`，通知项目负责人；必要时拆分任务 |
| 任务源不可用 | 本地记录待回写，恢复后幂等补写 |

## 6. S6 预算熔断

**前置条件**：任务已配置预算；模型调用经 LiteLLM 携带 `tenant_id` / `task_id`。
**后置条件**：预算充足则继续；超限则阻断调用并将任务置为 `blocked`。

```mermaid
sequenceDiagram
  autonumber
  participant AG as Agent
  participant LLM as LiteLLM
  participant LF as Langfuse
  participant SCH as 调度器
  participant TS as 任务源
  participant N as 通知
  participant AU as 审计

  AG->>LLM: 模型调用（virtual key + task_id）
  LLM->>LF: usage / cost
  LLM->>LLM: 预算校验
  alt 预算充足
    LLM-->>AG: 正常响应
  else 超预算
    LLM-->>AG: 拒绝
    LLM->>SCH: budget.block
    SCH->>TS: blocked(budget_blocked)
    SCH->>N: 通知负责人
    SCH->>AU: budget.block
  end
```

**关键规则**

1. 预算按租户、项目、任务三级配置；硬上限优先于软提醒。
2. 超限先阻断模型调用，不等待会话自然结束。
3. 任务进入 `blocked(budget_blocked)` 后，只有人能追加预算或关闭任务。
4. 成本数据以 LiteLLM / Langfuse 为准；任务账本只做汇总，不重复计费。
5. 熔断事件必须可追溯到具体任务、会话与模型。

## 7. S7 双 Agent 评审（可选）

**前置条件**：任务执行完成，项目启用交叉评审；评审 Agent 与执行 Agent 不同。
**后置条件**：评审结论作为证据附加，任务仍由人验收。

```mermaid
sequenceDiagram
  autonumber
  participant IA as 执行 Agent
  participant SCH as 调度器
  participant RA as 评审 Agent
  participant TS as 任务源
  actor H as 验收人

  IA-->>SCH: 交付证据
  SCH->>RA: 创建评审会话（diff + 验收标准）
  RA-->>SCH: verdict（pass / concerns）
  SCH->>TS: 附加评审证据（不改状态）
  TS->>H: 待验收（含评审结论）
  H->>TS: 最终通过 / 打回
```

**关键规则**

1. 评审 Agent 只给意见，不改变任务状态，不替代人验收。
2. 评审结论必须附理由与引用；`concerns` 要能定位到具体文件/行/验收项。
3. 评审会话与执行会话分离，避免同一 Agent 自证。
4. 评审成本计入任务账本；评审不通过不自动触发返工，由人决定。

## 9. 幂等与异常处理总表

| 风险点 | 机制 | 失败时行为 |
|---|---|---|
| 重复信号 | `source + external_id + fingerprint` 唯一约束 | 关联或忽略，不重复建任务 |
| 重复认领 | 租约 CAS / 状态机版本号 | 返回 409，不启动第二个会话 |
| 重复回写 | `session_id + evidence_hash` 幂等键 | 已存在则返回原结果 |
| 上下文重复提议 | 相似度 + 来源去重 | 合并或拒绝，不覆盖 |
| 审批重复提交 | `task_id + version + decision` 幂等 | 旧版本审批失效，返回冲突 |
| 上下文检索超时 | 超时 + 降级策略 | 默认空 pack + `context_degraded`；高敏项目可阻断 |
| 产物登记失败 | 重试队列 + 指数退避 | 超过阈值 `blocked(artifact_unavailable)` |
| 任务源不可用 | 本地事件表 + 恢复后补写 | 不双写第二任务源 |
| Agent 越权 | 权限矩阵 + PR-only + 禁止 `done` | 拒绝操作并审计 |

## 收录门与原型能力边界

信号与平台新建意图首先进入采集区，采集区不是任务状态，不属于八态任务板。收录必填项目、原始来源、标题、问题或目标描述、联系人/责任人以及项目范围确认；`external` 另需来源引用。缺项提示且不建卡，人为创建可选 `backlog` 或 `confirming`；待办意向实际先进入 `confirming`，不能默认就绪。收录门确认是否纳入项目，DoR 确认可执行，两者分开。

外部来源通过来源系统 SDK 对话留言，等待来源方反馈。平台创建任务由模拟 Agent 多轮澄清，只整理已提供事实，不执行编码。两条路径均须负责人确认问题解决并在会话台确认 DoR，才可进入待办。

问题、答复与历史、契约草稿和 DoR 保存于各任务对象。答复进入待确认，负责人确认解决后才允许通过 DoR 进入 `todo`；拖拽与派发也校验同一门禁。执行、返工和人工验收沿用现有模拟故事；操作统一记录为当前用户。`prototype/smoke-test.html` 覆盖缺项不建卡、收录后 backlog、两类来源路由、答复待确认阻塞、任务隔离和状态门，并保留原执行验收回归。

### 统一会话台与双层生命周期（交互模拟）

卡片的「打开 / 继续对话」跳转会话台并选中关联线程，不再打开澄清弹窗。左侧按全部 / Agent澄清 / SDK沟通 / 执行筛选，可叠加状态筛选；中间共享任务、阶段、会话状态、时间线和固定输入区；右侧提供问题确认、负责人 DoR、上下文确认、派发、暂停并澄清、恢复、人工验收 / 返工、取消 / 重开及查看任务。执行保留终端、diff 和证据；澄清复用消息、草稿与上下文。

任务采用八态：收录 `backlog` → 显式开始澄清 `confirming`（平台 Agent / 外部 SDK 共用）→ 必要问题解决并由负责人确认 DoR 后 `todo` → 唯一运行轮次 `in_progress` → 证据齐全 `in_review` → 授权人工 `done`。返工必须给理由，回待办后派发新轮次并保留历史；执行缺口暂停进入 `blocked`，旧计时停止，补齐并重新确认后回待办，通过「恢复执行」创建新轮次。取消进入 `canceled` 并停止执行；完成 / 取消重开按执行条件进入积压或待办，禁止直接执行。拖拽、输入与直接派发遵循同一门禁，Agent 永远不能确认完成。

澄清会话独立流转：`active`（进行中）、`waiting_reply`（等待回复）、`awaiting_confirmation`（等待负责人确认）、`resolved`（已解决）、`closed`（已关闭）。执行会话为运行 / 暂停 / 完成 / 失败 / 关闭。SDK 留言发送后记录等待来源方反馈；回调去重并校验所属任务、轮次及关联留言，已结束线程与任务拒绝迟到回调。已解决线程只读，新补充须明确「重新澄清」开启下一轮，撤销 DoR；未执行任务回积压，旧轮次消息保留。仅查看历史不改变业务状态。

澄清保存在任务及历史轮次，通过带 `kind` 的独立投影与执行列表合并，不写入执行 `state.sessions`，不参与运行数和成本统计。重要操作记录 activity / audit。四种采集预设仍只填表，不跳过收录和执行条件。全部为单页面内存模拟，关闭与切换保留消息草稿，刷新恢复种子数据；未接入真实 Agent、SDK 送达、身份鉴权、分布式执行租约或持久化。
