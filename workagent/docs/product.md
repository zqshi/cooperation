# WorkAgent 产品介绍与设计思考

WorkAgent 面向中小企业，把私人 AI 文本工作、周期性执行与团队交付组织在同一个员工 Portal 中，并由企业控制台提供受控的 Agent 与资源配置。它希望减少“结果散落在聊天里、工作没人接续、执行与验收混在一起”的摩擦。

以下人物和问题是产品设计假设，不是已完成用户研究的结论；尚无真实客户效率、留存或 ROI 数据。

## 用户与问题

| 用户 | 待解决的问题 | 当前产品回应 |
| --- | --- | --- |
| 业务员工 | 重复说明个人职责与输出偏好，临时文字结果难以回看 | 私人搭档档案、版本化指令、默认项目内的执行结果 |
| 有周期工作的人 | 固定时间要重复提交同一段文本任务 | 私人日程、手动触发、真实执行历史与错误 |
| 项目负责人和执行成员 | 谁负责、尝试过什么、谁确认完成不清楚 | 持久任务、指派、执行尝试、提交与独立验收 |
| 企业管理员与构建者 | 工具和知识连接带来权限、费用和副作用 | 企业 Agent 发布、评测、审批、配额与审计 |
| 平台运营者 | 企业开通与企业内容权限容易混淆 | 单独平台会话、新企业初始化与聚合运营视图 |

## 四种工作容器

**私人搭档**承载个人职责与偏好，归当前企业中的本人独占。普通有效成员即可开通，不需要企业构建者权限。保存档案会编译为生效指令版本；当前仅文本执行，没有个人工具、知识挂载、长期记忆、技能、设备或个人 IM 路由。

**私有默认项目**是每个企业/用户的真实项目和独占工作容器，由系统创建并固定在目录前方。不能共享、转移、删除或更名。它可以承载真实规划任务，也展示本人未归属项目的执行、审批与产物。后者保留空的原始项目归属，展示上下文不会重写历史，更不会变成虚构任务。

**共享项目**围绕明确成员、任务和验收组织团队工作。任务独立于执行，可以纯人工推进，或指定已发布企业 Agent 并创建真实尝试。企业及平台管理员也必须具有显式项目成员资格。私有搭档不能指派为项目任务执行者，包括默认项目内任务。

**个人自动化**保存“何时用我的私人搭档执行这段文本”，不生成周期项目任务。支持单次、周期、时区和 cron，执行结果在站内查看，无工具、知识、通知或 IM 投递。日程与实际发生记录分离，便于区分未触发、跳过、执行中、失败和成功。完整规则见 [自动化语义](personal-automation.md)。

## 当前可走通的用户旅程

1. 员工登录 Portal，开通搭档，填写职责与偏好；首页查看或编辑档案并发起文本工作。模型未配置时明确提示联系管理员，不以“在线”替代真实可用性。
2. 员工在「自动化」填写文本和时区日程，查看服务端计算的下次时间；可手动触发，进入实际执行查看结果或错误，再返回对应日程。
3. 员工进入「项目」目录，打开默认项目或已加入的共享项目；在看板新建任务、明确负责人和上下文。人工任务创建无需模型。
4. 成员在共享项目为任务选择企业 Agent，发起尝试，查看运行与工具审批。审批只是允许动作，不是认可交付。成功尝试后提交任务，由不同的项目经理验收；失败可以保留原尝试再重试。
5. 管理员在企业控制台配置企业资源、构建及评测 Agent、发布快照，再由显式授权的员工使用。渠道需签名校验与身份绑定；网页使用不依赖 IM。

## 为什么这样设计

**任务应比执行活得更久。** 一次模型调用会失败、取消或重试，不能因此抹掉工作目标和责任。任务持有标题、描述、负责人、版本与状态，尝试引用实际运行；删除规划任务后，执行仍保留原项目归属。代价是用户需要理解“任务完成”和“运行成功”两个层次。

**私人便利和团队责任需要不同边界。** 私人指令不因管理员身份而可读；共享工作必须显式加入项目。默认项目减少个人结果的散落，同时不假装私人执行已经成为团队资产。代价是私有默认项目只有本人，无法满足独立验收所需的另一位经理；需团队验收的工作应放到共享项目。

**自动化首先要解释没有发生什么。** 系统停机后仅补一个到期周期，再跳到未来；同日程有活跃运行时记为跳过，避免无限追赶与重叠。暂停只阻止后续定时派发，不取消已运行工作；终止会取消活跃关联运行。可预测性优先于尽可能多地补跑，但用户仍需检查失败和跳过。

**人的责任不能用成功状态替代。** 工具审批、运行结果认可、任务验收各自有授权和状态约束。执行者不能自行验收；外部副作用不承诺绝对只发生一次，不确定调用应核对供应商记录。产品因此保留人工判断，而非把审批页面当作风险已经消失。

**管理界面表达的是权限范围。** 企业构建、员工工作与平台运营使用不同壳和服务端授权。配置存在、按钮可点、聚合计数有值，都不能证明供应商连通或产品已具备完整企业运营闭环。

## 当前能力与缺口

已实现私人档案、受限文本执行、自动化、真实默认项目、项目任务/尝试/审批/产物/成员及独立验收；企业侧有 Agent 构建发布与知识、工具、渠道、审计等工程能力。控制台提供这些能力的管理壳，整体业务体验仍需真实场景验收。

项目背景可存储，但不会自动注入任务执行；没有项目聊天、项目知识发布、手工资产上传、资产版本体系或完整项目元数据编辑。个人技能/知识/记忆/设备不开放，私人搭档不承担企业渠道默认路由。平台生命周期限于新企业开通、聚合详情、名称/套餐配置，没有完整暂停/注销闭环。真实供应商、托管 CI、目标部署与恢复演练仍需独立验证，见 [运维](operations.md)。

## 待验证问题

- 员工是否能理解搭档、默认项目和共享任务的关系，还是需要更明确的工作引导？
- 哪些周期文本任务在没有业务数据工具时仍有持续价值？
- 独立验收对小团队的质量收益是否抵得过额外操作？默认项目的限制是否清晰？
- 项目背景若要注入执行，谁负责授权、版本和引用来源？
- 试点应记录任务验收率、返工原因、失败/跳过原因和人工接管成本；这些是候选观测指标，不是已达成效果。
