# Personal automation

任务协作 contains two sibling tabs: 自动化 (`/automations`, `/automations/:id`) and 项目 (`/projects`). Opening the group lands on 自动化. Both retain the existing root personal-Agent provision/loading/error gate. Private automation retains null actual project provenance (013 constraints), while its owner-only executions appear in the real default project fallback. Shared project planning, membership and independent acceptance stay unchanged. There is no independent personal history page.

## Owned schedule and execution

Migration 013 adds `personal_automation` and `automation_occurrence`; prior migrations are preserved. Each schedule has immutable org, owner and owned private personal Agent. Every list/detail/history/mutation binds the authenticated org/user, with no administrator read bypass. Composite foreign keys and triggers forbid foreign-Agent and cross-user/project run attachments. DTOs reject owner, Agent, project, tool, notification and other forged fields.

Create/edit supports once and recurring schedules, IANA timezone, daily/weekly/monthly presets and five-field cron. Public `cron-parser` 5.10.2 supplies timezone/DST/calendar parsing. Minute sets must be separated by at least 15 minutes on the circular clock (a conservative rule even for sparse hour/day selections). Missing monthly dates are skipped. Once accepts a future RFC3339 instant through 2099; the UI resolves its selected IANA wall time and rejects nonexistent/ambiguous DST times. Recurring DST behavior follows cron-parser. Returned next execution is the server's actual persisted instant, displayed in the schedule timezone.

Edits use optimistic versions and replace the next occurrence; dispatched runs retain their actual compiled revision/input. Pause stops future scheduled dispatch only; manual execution remains available. Resume computes the next future occurrence and refuses an expired once schedule (edit its date first). Terminate is irreversible and cancels active linked runs; delete additionally removes the schedule from the directory. Both preserve actual run/history records and cannot undo an already completed output. A completed once schedule may be edited/rescheduled or manually triggered. Deleted detail/history remains accessible only to its owner by existing deep link; there is no fabricated 30-day retention promise.

`/v1/automations` provides create/list; `/:id` provides get/edit; `/:id/actions` provides versioned pause/resume/terminate/delete; `/:id/trigger` requires a bounded client idempotency key; `/:id/history` exposes actual associated run status/output/error. Lists/history use deterministic SQL pagination (default 20, maximum 100). History links authorize through the existing run detail/cancel API then resolve into the owner’s default project context; detail returns to its actual automation occurrence.

## Durable dispatch

The existing worker polls every five seconds, with one in-process tick at a time and batches of at most 50 schedules by default (hard cap 100). Existing org run-creation advisory locks establish a consistent order with quota/run creation; due schedule rows use `FOR UPDATE SKIP LOCKED`. Edits, triggers and termination share that serialization. A unique schedule/occurrence key prevents duplicate scheduled dispatch; manual retries use a separate stable key. Advancement, occurrence, run, quota increment, existing execution outbox job and dispatch audit commit in one transaction. Failure/rollback before commit leaves the schedule due for retry; committed jobs use existing heartbeat leases, recovery, fenced acknowledgement and run advisory execution locks.

After downtime, a recurring schedule dispatches at most its one persisted due occurrence, then advances directly beyond the tick time. No unbounded backlog is generated. Once dispatches once. If this schedule already has a queued/running/waiting-approval run, the occurrence is recorded as skipped with its reason and the schedule advances. Overlap is per schedule, not a new enterprise-wide execution policy. No catch-up notification or IM delivery exists.

Dispatch locks and rechecks active org membership, actual personal ownership and the current published compiled revision. Dispatch rejection records a redacted failed occurrence using a savepoint; partial conversations/runs/quota/outbox writes roll back. Revocation or unavailable personal release pauses future scheduling. Existing engine checks reject revoked queued/running identities. Mutation and cancellation audit failures roll back the state change and run cancellation; dispatch audit failure rolls back schedule advancement and the entire enqueue.

The personal text-only policy remains unchanged: no tools, knowledge attachments, memory, project access or publication override. Normal quotas and execution run handling apply. Missing model credentials cause an actual failed run (`Model credentials required`), never synthetic production success. UI explains unavailable models, private text limits and station-only history. There is no implicit IM dependency, notification toggle, vendor readiness claim or external exactly-once promise.
